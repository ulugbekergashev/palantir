# Palantir — план ядра: реальная работа в клинике

Дата: 2026-10-18. Цель: чтобы Palantir **по-настоящему** работал в клинике — принимал и разбирал обращения из Telegram и Instagram, звонки (с записью), камеры, и всё это сходилось в одной базе с DentaCRM. Утренние планы и стенд — второстепенное, здесь их нет.

## 0. Честная картина сейчас

| Область | Что есть в коде | Проверено на настоящем сервисе | Главные дыры |
|---|---|---|---|
| Telegram-бот (клиенты) | приём, ответ ИИ, черновик/авто, запись к врачу | **нет** (только фальшивый Telegram) | заявки «перезвоните» не становятся задачей; всё идёт только владельцу |
| Личный Telegram клиники | GramJS: вход по коду, чтение, ответ | **нет** | то же |
| Instagram | **браузер** (Playwright) под логином владельца, приватный web-API Instagram | **нет** | нет официального API Meta; риск блокировки; нет догрузки при всплеске сообщений |
| Звонки | только ручная отправка записи в бота → разбор текстом; ИИ-голос (tgvoice, параллельная работа) | **нет** | нет приёма звонков АТС/MicroSIP, нет автозаписи, звонок не связан с клиентом, разбор не сохраняется |
| Камеры | ffmpeg + распознавание людей, зоны, сверка с CRM | **нет** (только тестовая картинка ffmpeg) | точность не измерена; владелец не получает оповещений |
| DentaCRM | чтение дня/периода/пациентов, запись к врачу, платежи/расходы | частично (локальная версия скриптами), облако — **нет** | нельзя перенести/отменить запись, нет связи «клиент ↔ пациент», нет заявок |
| Единый клиент | Telegram-бот и личный Telegram склеиваются | — | Instagram и звонки — отдельные люди; склейки по телефону нет; дубли |

Вывод: каналы написаны, но **ни один не проверен вживую**, и они не сходятся в одну картину клиента. Это и есть работа.

## 1. Как должно работать (один реальный случай от начала до конца)

1. Пациентка пишет в Instagram: «Здравствуйте, перезвоните мне на 90 123 45 67 после шести».
2. Palantir отвечает ей (черновик на одобрение или сам — по настройке клиники): «Хорошо, администратор позвонит вам после 18:00».
3. Создаётся **заявка** «Перезвонить» с номером `+998 90 123 45 67`, временем «после 18:00», источником «Instagram» и цитатой сообщения. Номер сохраняется в карточку клиента; если такой номер уже есть у пациента DentaCRM или у клиента из Telegram — это **один и тот же человек** (склейка).
4. Заявка мгновенно приходит **регистратуре** в Telegram с кнопками «📞 Позвонить», «✅ Сделано», «⏰ Не дозвонился» (владелец видит копию или только сводку — настройка).
5. «📞 Позвонить» → MicroSIP на компьютере регистратуры набирает номер. Разговор **записывается автоматически**.
6. После звонка запись расшифровывается (узбекский, с разделением голосов), ИИ делает разбор: что хотел клиент, записался ли, что пообещали, следующий шаг. Звонок прикрепляется к карточке клиента и к заявке; если записались — запись видна в DentaCRM; если нет — следующий шаг.
7. Пропущенный входящий звонок → сразу заявка «Перезвонить» регистратуре.
8. Всё это видно в панели: карточка клиента — все сообщения всех каналов, звонки с записью и расшифровкой, заявки, записи DentaCRM.

## 2. Решения по архитектуре

**А. Единая карточка клиента.** Номер телефона приводится к одному виду (последние 9 цифр) и является ключом склейки. Когда у клиента появляется номер (сам написал, поделился контактом, позвонил, введён вручную), Palantir ищет других клиентов и пациента DentaCRM с этим номером и **объединяет**: переписки всех каналов, заявки, звонки, задачи переходят в одну карточку. У карточки — ссылка на пациента DentaCRM.

**Б. Заявки — отдельная сущность.** Тип: перезвонить / записаться / вопрос / жалоба. Поля: номер для связи (может отличаться от номера профиля), удобное время, источник и цитата, статус (открыта → сделано / не дозвонились / отменена), кто взял, связанные звонки и запись к врачу. Создают заявки: ИИ из переписки (новые поля в разборе сообщения), пропущенный звонок, голосовой агент (`leave_request`), владелец или ассистент. Открытая заявка дольше срока (по умолчанию 15 минут для «перезвонить») — повторное напоминание.

**В. Регистратура (сотрудники).** Кроме владельца — Telegram администраторов. Ссылка подключения из панели; роль «регистратура» получает заявки и карточки ответов клиентам; деньги и сводки — только владельцу.

**Г. Телефония: MicroSIP прежде всего.** MicroSIP работает с любым SIP-оператором (UTEL, Uztelecom, Sipuni, OnlinePBX): не нужно ждать API от оператора. Уже проверено в dentalocal (MicroSIP 3.22.18): хуки событий `cmdIncomingCall / cmdCallAnswer / cmdCallStart / cmdCallEnd / cmdOutgoingCall` через маленький exe без оболочки, набор номера `microsip.exe <номер>`. В настройках MicroSIP есть `autoRecording`, `recordingPath`, `recordingFormat` (mp3 через lame_enc.dll) — Palantir включает автозапись в свою папку и забирает файлы. Облачные АТС (webhook + ссылка на запись) — вторым шагом через тот же интерфейс «событие звонка». ИИ-голосовой агент (tgvoice, Asterisk — параллельная работа) не трогаю, он подключается через существующий голосовой шлюз.

**Д. Instagram — официальный API Meta.** «Instagram API with Instagram Login» (без страницы Facebook), право `instagram_business_manage_messages`, вебхук `messages`. Отвечать можно в течение 24 часов после последнего сообщения клиента; для поддержки — тег `human_agent` до 7 дней. Вебхуку нужен публичный HTTPS-адрес, а у Meta-приложения он один на все клиники → **Palantir Hub** (маленький облачный сервис): принимает вебхуки, по id аккаунта пересылает событие нужной клинике через **исходящее** WebSocket-соединение (на компьютере клиники порты не открываются). Ответ клиника отправляет сама в Graph API своим токеном (токен хранится зашифрованным у клиники). Доступ: пока нет Advanced Access, работают аккаунты, добавленные в роли приложения — так подключаем первые клиники; параллельно подаём App Review + Business Verification. Браузерный способ остаётся запасным и выключен по умолчанию.

**Е. DentaCRM.** Добавить: поиск/привязку пациента к карточке, список записей пациента, перенос/отмену записи, статус («пришёл/не пришёл») — там, где API DentaCRM это позволяет; чего нет в API — добавить в сам DentaCRM (это ваш продукт).

**Ж. Проверка вживую — правило.** Для каждого канала — скрипт проверки на настоящем сервисе (`npm run live:<канал>`), который проходит путь из раздела 1 и печатает, что реально произошло. Фальшивые сервисы остаются только для быстрых автотестов.
